# Directriz de Trabajo con GitHub — INNOVA

> Convención oficial del repositorio. Adoptada en issue #2 (PR del Sprint 0 Fase 0).
> Estas reglas son **obligatorias** para todo trabajo de desarrollo en INNOVA.
> Aplicable también a agentes de IA (Copilot, Claude, Cursor) que operen sobre el repo.

---

## 1. Branch antes de cualquier cambio

- **Nunca empezar implementación sobre `main`**.
- Crear siempre un branch de trabajo primero:
  - Con issue: `issue-<id>-<stream>-<tema-corto>`
  - Sin issue aún: `wip-<yyyymmdd>-<tema-corto>` (solo casos excepcionales: bootstrap, spike, exploración)
- El branch debe crearse desde `main` actualizado (`git pull --ff-only origin main`).
- Todos los cambios quedan aislados en ese branch.

Streams válidos (también usados como labels — ver §8): `core`, `canvas`, `flows`, `reports`, `pcf`, `plugins`, `docs`, `ci`.

### Ejemplos de nombres

```
issue-23-canvas-pmo-evaluacion
issue-42-flows-notificar-jefatura
issue-17-core-tabla-iniciativa
issue-8-docs-adr-business-units
wip-20260523-spike-environment-variables
```

---

## 2. Issue primero, implementación después

- No implementar ninguna actividad sin un issue previo en GitHub.
- Crear **un issue por actividad concreta** con los siguientes campos:

| Campo                         | Contenido                                            |
| ----------------------------- | ---------------------------------------------------- |
| Objetivo                      | Qué se quiere lograr                                 |
| Alcance                       | Qué archivos/módulos toca                            |
| Criterios de aceptación       | Condiciones observables que confirman que está listo |
| Validaciones/tests requeridos | Qué tests deben pasar                                |
| Riesgos                       | Efectos secundarios posibles                         |

- Agregar labels y prioridad cuando aplique (§8).
- Vincular el issue al sprint/plan vigente en [`docs/plan/`](../plan/).

---

## 3. Implementar y validar por issue

- Implementar solo lo definido en el issue.
- Ejecutar las validaciones/tests relevantes para ese issue.
- Si algún test falla, corregirlo en el mismo branch antes de avanzar.
- Marcar el issue como listo para cerrar solo cuando los criterios de aceptación estén cumplidos.

---

## 4. Trazabilidad en commits

Usar mensajes de commit estructurados según [Conventional Commits](https://www.conventionalcommits.org/):

```
<tipo>(<scope>): <resumen corto en presente, imperativo, en inglés>

Refs #<número de issue>
[cuerpo opcional con detalle]
[evidencia breve de validación]
```

### Tipos permitidos

| Tipo       | Cuándo usarlo                                 |
| ---------- | --------------------------------------------- |
| `feat`     | Nueva funcionalidad                           |
| `fix`      | Corrección de bug                             |
| `chore`    | Tareas de mantenimiento, configuración        |
| `test`     | Agregar o corregir tests                      |
| `docs`     | Solo documentación                            |
| `refactor` | Reestructuración sin cambio de comportamiento |
| `style`    | Cambios de formato sin cambio de comportamiento |
| `perf`     | Mejora de performance                         |
| `ci`       | Cambios al pipeline de CI/CD                  |

### Scopes en INNOVA

Usar los mismos streams que en branches y labels: `core`, `canvas`, `flows`, `reports`, `pcf`, `plugins`, `docs`, `ci`. También `m1`-`m14` para módulos del WBS y `f1`-`f6` para fases transversales.

### Reglas

- Descripción en inglés, modo imperativo, sin punto final, máx 72 chars.
- Incluir referencia al issue en el cuerpo: `Refs #123`.
- Agregar evidencia breve de validación cuando aplique (ej: `13/13 tests passing`, `smoke test in DEV OK`).
- Usar `Closes #123` solo cuando el merge debe cerrar el issue automáticamente (típicamente en el commit del PR final).
- Un commit, un cambio lógico — si hay que poner "y" en la descripción, probablemente son dos commits.

### Ejemplo de commit completo

```
feat(canvas): add pantalla solicitante with consecutivo generator

Refs #23
- Implements 3 sections: información general, información de iniciativa,
  tabla dinámica de colaboradores
- Consecutivo generated by Helper flow with row-level lock
- Smoke test en DEV OK con 5 escenarios
```

## 5. PR, merge y limpieza

### Abrir el PR

- Siempre desde el branch temporal hacia `main`.
- La descripción del PR debe incluir:

```markdown
## Resumen técnico

[Qué hace este PR y por qué]

## Issues relacionados

Closes #23
Refs #24, #25

## Evidencia de tests

- Smoke test pantalla en DEV: 5/5 escenarios OK
- Solution check: 0 errores, 2 warnings (documentados)
- Lint Power Fx: clean

## Riesgos

[Efectos colaterales posibles o deuda técnica introducida]
```

### Después del merge

1. Confirmar que los issues vinculados quedaron cerrados.
2. Eliminar el branch temporal (local y remoto):

```bash
git checkout main
git pull --ff-only origin main
git branch -d issue-23-canvas-pmo-evaluacion
git push origin --delete issue-23-canvas-pmo-evaluacion
```

## 6. Regla operacional permanente

| Regla                                           | Consecuencia de incumplimiento |
| ----------------------------------------------- | ------------------------------ |
| Sin branch → sin implementación                 | Rollback directo               |
| Sin issue → sin implementación                  | El trabajo no cuenta           |
| Sin tests → no se cierra el issue               | Queda abierto hasta evidencia  |
| Sin PR mergeado y branch limpio → no está hecho | Trabajo incompleto             |

---

## 7. Flujo completo de una tarea

```
1. Actualizar main
       ↓
2. Crear GitHub issue con criterios de aceptación
       ↓
3. Crear branch  issue-<id>-<stream>-<topic>  desde main
       ↓
4. Implementar solo lo del issue
       ↓
5. Ejecutar tests → si falla, corregir en el mismo branch
       ↓
6. Commit con mensaje estructurado + Refs #<id>
       ↓
7. Abrir PR con evidencia
       ↓
8. Aprobar y mergear a main
       ↓
9. Confirmar cierre del issue
       ↓
10. Eliminar branch local y remoto
```

## 8. Convenciones de labels en GitHub

Tipo de issue:

| Label      | Uso                                    |
| ---------- | -------------------------------------- |
| `activity` | Issue de actividad concreta            |
| `bug`      | Defecto o comportamiento incorrecto    |
| `epic`     | Issue contenedor de múltiples actividades |
| `blocked`  | Bloqueado por dependencia externa      |

Prioridad:

| Label | Uso                                    |
| ----- | -------------------------------------- |
| `p0`  | Prioridad crítica (bloquea producción) |
| `p1`  | Prioridad alta                         |
| `p2`  | Prioridad media                        |

Stream (alineado con scopes de commit y prefijos de branch):

| Label     | Uso                                       |
| --------- | ----------------------------------------- |
| `core`    | Dataverse — tablas, columnas, BU, roles   |
| `canvas`  | Power Apps Canvas — pantallas             |
| `flows`   | Power Automate                            |
| `reports` | Power BI                                  |
| `pcf`     | PCF Controls (TypeScript + React)         |
| `plugins` | Plug-ins .NET de Dataverse                |
| `docs`    | Documentación, ADRs, runbooks             |
| `ci`      | CI/CD pipelines, scripts                  |

Cada issue lleva al menos: 1 tipo + 1 prioridad + 1+ streams.

## 9. Checklist rápido antes de abrir un PR

- [ ] Branch creado desde `main` actualizado
- [ ] Issue existente con criterios de aceptación definidos
- [ ] Implementación acotada al scope del issue
- [ ] Tests/smoke tests relevantes ejecutados y pasando
- [ ] Commits con mensaje estructurado y `Refs #<id>`
- [ ] PR description incluye resumen, issues, evidencia de tests y riesgos
- [ ] Sin archivos temporales ni credenciales en el diff
- [ ] Solutions de Dataverse exportadas y unpacked si el cambio toca `solutions/`
- [ ] `CHANGELOG.md` actualizado si el cambio afecta el comportamiento

---

## Apéndice — Excepciones documentadas

Las siguientes situaciones permiten desviarse temporalmente de §2 (issue primero), siempre que se documente:

- **Bootstrap inicial del repo**: branch `wip-<yyyymmdd>-...` permitido para crear estructura base que luego habilita abrir issues.
- **Hotfix crítico**: branch `hotfix-<yyyymmdd>-<tema>` desde `main`, con issue retroactivo abierto antes del PR.
- **Spike de exploración**: branch `wip-<yyyymmdd>-spike-<tema>`, no merge — siempre se cierra con un issue formal que sí siga la directriz.
